# Grudge Vault 分阶段开发计划

> 本计划按“先形成纵向闭环，再逐步增强记忆与 Agent 能力”组织。阶段用于表达价值顺序和依赖关系，不是不可调整的范围合同；获得真实数据和使用反馈后，可以合并、拆分或前移任务。

## 1. 交付原则

- 每个阶段都交付一个可运行、可演示、可迁移的版本。
- 优先走通完整用户路径，再扩充同类功能和模型效果。
- 原始输入先可靠保存，AI 处理失败或暂时不可用不影响记录。
- 数据模型和迁移保持向前兼容，实验性分析结果允许重建。
- 用少量真实、去隐私化的 fixtures 验证 Day One、附件和历史回填。
- 阶段验收看用户能完成什么，不以代码量或页面数量衡量。

## 2. 里程碑总览

| 阶段 | 主题 | 用户获得的主要价值 | 建议发布点 |
| --- | --- | --- | --- |
| Phase 0 | 可运行基础 | 可以安全创建和打开本地工作区 | Developer Preview |
| Phase 1 | 事件记录闭环 | 可以记录、编辑、检索事件并保存附件 | Internal Alpha |
| Phase 2 | Day One 与历史回填 | 过去的日记可导入、去重并产生待确认事件 | Alpha |
| Phase 3 | 关联、检索与回顾 | 可以从人物和时间线理解重复发生的问题 | Beta Foundation |
| Phase 4 | Harness Agent 与策略分析 | 可以通过对话检索记忆、分析事件并形成行动选项 | First Useful Beta |
| Phase 5 | Evidence Vault 与 Case | 可以面向权益问题整理来源、缺口和材料包 | Evidence Beta |
| Phase 6 | 本地智能与持续记忆 | 更自动的处理、回顾和多数据源接入 | Ongoing |

首个“功能齐全且日常可用”的目标是完成 Phase 4。Phase 1 已经能可靠记账，Phase 2 能利用既有 Day One 数据，Phase 3—4 则让长期记忆和 Harness Agent 的差异真正显现。

## 3. Phase 0：可运行基础

> 实施状态：Developer Preview 基础已于 2026-08-23 落地；后续真实平台反馈仍可能推动加固。

### 目标

搭建桌面应用、领域包、数据库迁移和对象保险库的最小骨架，让后续功能建立在可恢复的数据基础上。

### 主要工作

- 初始化 Electron + React + TypeScript Monorepo；
- 建立 main、preload、renderer 的进程边界和类型化 IPC；
- 创建 Workspace、配置与数据库迁移机制；
- 建立 SQLite 连接、WAL、事务和基础 repository；
- 实现对象保险库原型：复制、SHA-256、内容寻址、原子写入与加密写入；
- 建立 OS Keychain 对接和 Workspace Key 的最小密钥流程；
- 建立 SQLite-backed Job Runner 和任务状态 UI；
- 配置 lint、typecheck、unit test、build 和最小 CI；
- 编写首批 ADR：桌面技术栈、对象保险库、修订模型、模型 Adapter。

### 纵向演示

用户创建工作区，拖入一个文件；应用生成 Asset、保存对象、显示哈希；重启应用后仍能浏览该记录。

### 完成信号

- 新环境可以通过文档完成开发启动和构建；
- 数据库从空版本迁移到当前版本，并可重复执行；
- 中途退出后任务可以恢复或明确重试；
- Renderer 无法绕过 Preload 任意读取本地文件。

## 4. Phase 1：事件记录闭环

> 实施状态：Internal Alpha 已于 2026-08-24 落地；真实使用反馈将继续用于加固交互与数据迁移。

### 目标

让产品完成最基础但可靠的“发生事情 → 记录 → 修改 → 查找”闭环。

### 主要工作

- 实现 Event、EventRevision、SourceItem、Person、Asset 和 Clarification 基础模型；
- 提供 Chat 风格的快速输入，并先保存原始 Message；
- 通过简单规则或模型 Adapter 生成 Event Draft；
- 支持事件详情、确认、编辑、归档和修订历史；
- 支持人物、时间、情绪、利益和事实/解释的基础编辑；
- 支持附件拖入、原件哈希、来源关联和下载/查看；
- 原始附件默认加密入库，派生任务通过受控接口读取；
- 建立 FTS5 事件搜索和基础过滤；
- 实现工作区备份与恢复的第一版。

### 纵向演示

用户在对话中输入一段经历，确认生成的事件，补充人物和大致时间，添加一张截图；随后通过人物或关键词找回事件，并查看每次修改的来源。

### 完成信号

- 模型不可用时，原始输入仍保存并可手动建事件；
- “约 9 月”“金额未知”等信息不会被强制精确化；
- 原始附件与 OCR 等派生内容使用不同对象；
- 任何事件修改都可追溯到 revision；
- 备份恢复后 Event、Source、Asset 引用保持有效。

## 5. Phase 2：Day One 与历史回填

> 状态：Phase 2 Core 已实现。Import Folder 监听、超大 ZIP 专项优化、OCR/ASR 和统一来源搜索仍按后续阶段推进；两份真实去隐私化 fixture 的兼容验收等待安全样本输入。

### 目标

把用户已经存在的 Day One 日记转化为可逐步整理的 Source Memory，开始补回过去可能遗忘的事件。

### 主要工作

- 收集多版本、去隐私化的 Day One JSON ZIP fixtures；
- 实现 ZIP 校验、流式解包、Import Run 和错误报告；
- 解析 JournalEntry、时间、时区、标签、地点和媒体引用；
- 按 Entry UUID 幂等导入，保存修改后的 SourceVersion；
- 将照片、视频、音频和 PDF 导入对象保险库；
- 建立批量 Backfill 任务和暂停、恢复、取消体验；
- 实现 Candidate Event Detector 的第一版；
- 实现待补全箱：确认、补充、合并、忽略候选事件；
- 为每个提取结果保留 JournalEntry 引用和提取器版本。

### 纵向演示

用户导入一份 Day One ZIP。应用展示导入条目和媒体数量，后台从日记中发现候选事件；用户补充一笔大致金额并确认事件。再次导入同一份 ZIP 时不产生重复数据。

### 完成信号

- 同一 ZIP 重复导入结果幂等；
- 单条坏数据或缺失媒体不会使整个批次回滚；
- 候选事件可以追溯到原始日记段落；
- 模型遇到“上次那件事”时创建 Clarification，而不是补造经过；
- 用户可以控制 Backfill 的范围和处理节奏。

### 可并行探索

- 监听用户指定的 Import Folder；
- 对超大 ZIP 做性能基准；
- 调研 Day One 新版本字段，但不直接依赖其内部数据库。

## 6. Phase 3：关联、检索与回顾

### 目标

把孤立 Event 组织成可理解的长期记忆，让用户看见时间、人物和重复模式。

### 主要工作

- 人物别名、疑似同一人物和用户确认合并；
- Event Relation：相似、先后、同一主题、同一 Case；
- Timeline 与 People 视图；
- JournalEntry、Event 和 Transcript 的统一搜索结果；
- 可选本地 Embedding Adapter 与混合检索；
- 相关事件建议，并保留算法/模型依据；
- 月度、季度和自定义区间回顾；
- 待补全项优先级：普通、重要、权益相关；
- 搜索与回顾结果引用来源，支持一键回到原记录。

### 纵向演示

用户打开某个人物页面，看到按时间排列的共同事件；系统发现多次问题集中在项目汇报前后。用户可打开每条原始来源，纠正误关联，并重新生成回顾。

### 完成信号

- 关键词搜索在不启用模型时可完整使用；
- 语义召回关闭、重建或更换实现不会影响 Event 数据；
- 人物合并可撤回，不丢失原始别名；
- 模式结论能列出支持它的具体事件；
- 用户纠正关联后，后续回顾使用新的当前投影。

## 7. Phase 4：Harness Agent 与策略分析

### 目标

让对话成为统一操作入口：Agent 能记录、检索、补全和回顾，并基于可引用的本地记忆提供结构化分析与行动选项。

### 主要工作

- 建立 Tool Registry、版本化 Schema 和 Agent Run Log；
- 实现 Record、Retrieve、Review 和 Strategy 工具组；
- 建立 Intent Router 与按需 Context Builder；
- 让 Agent 回答引用 Event、Source、Asset 和 Transcript；
- 实现“事实 / 争议 / 未知 / 解释 / 情绪”分析模板；
- 实现历史相似事件、利益、风险和可选行动比较；
- 支持通过对话逐项回答 Clarification；
- 实现 Private / Enhanced 模型配置与最小上下文脱敏；
- 建立固定情景评测，跟踪事实混淆、无依据补全和错误工具调用。

### 纵向演示

用户问“帮我复盘这一年和某人的成果归属问题”。Agent 调用搜索、人物历史、时间线、证据和分析工具，返回有来源的事实链、重复模式、未知项与多个行动选项；用户随后通过对话补全其中一条事件。

### 完成信号

- Agent 的写入动作全部经过领域工具并形成 revision；
- 回答中的关键事实可跳转到本地来源；
- 未知信息不会因多轮对话被逐渐描述成事实；
- 关闭 Enhanced 模式后不发生外部模型调用；
- 模型失败时，普通浏览、搜索和编辑功能仍可使用。

## 8. Phase 5：Evidence Vault 与 Case

### 目标

当事件涉及权益争议时，帮助用户系统地整理材料、缺口和时间线，并生成可核验的 Case Binder。

### 主要工作

- 完善工作区锁定、密钥恢复、轮换和加密迁移体验；
- 原始对象完整性巡检与清晰的异常处理；
- Evidence 视图：原件、来源、哈希、派生物和关联事实；
- Case 创建、事件选择、人物、金额、争议点和待确认问题；
- Case Timeline 和缺失材料清单；
- 生成 PDF 说明、证据目录、manifest 和 SHA-256 清单；
- 导出前预览、选择范围和敏感信息处理；
- 用不同地区/时点的占位式 Legal Information Adapter 验证“动态核验”流程。

### 纵向演示

用户把若干历史事件加入一个 Case，选择相关聊天截图、录音和文件。应用展示事实与材料的对应关系、缺失项和哈希状态，并导出一个带 manifest 的 Case Binder。

### 完成信号

- Case 只引用原始材料，不会把 OCR 或模型总结冒充原件；
- 导出包可独立校验文件哈希；
- 删除、替换或损坏材料时，Case 明确显示引用状态；
- 法律相关回答区分材料整理、一般信息和需要外部核验的问题；
- 导出行为由用户明确触发并可预览内容。

## 9. Phase 6：本地智能与持续记忆

### 目标

在基础闭环稳定后提高自动化程度，让产品长期陪伴使用，而不牺牲可解释性和用户控制。

### 候选方向

- 本地 LLM、Embedding、OCR 和 ASR 的安装与硬件适配；
- Day One Import Folder 监听和增量处理；
- 图片 OCR、音频时间戳转写、视频音轨与关键帧；
- 主动月度/季度 Review 和高价值待补全提醒；
- 新数据源 Adapter，例如 Markdown、聊天导出、邮件归档或任务系统；
- 可选的多设备加密同步；
- CLI、移动伴侣端或浏览器采集入口；
- 可配置 Agent Skill 与第三方工具插件。

这一阶段按用户反馈排序，不预先承诺所有方向。优先选择能显著减少记录成本或提高历史记忆价值的能力。

## 10. 跨阶段工作流

### 10.1 数据迁移

- 每次 schema 变更提供向前迁移和备份提示；
- 长期实体使用稳定 ID；
- 可重建索引和分析结果不混入不可重建的原始数据；
- 在发布前用旧版本工作区快照做升级测试。

### 10.2 隐私与安全

- 每个阶段做依赖和桌面进程边界检查；
- 测试日志和错误报告是否泄露正文；
- External Model Adapter 增加数据发送审计；
- 导入压缩包按不可信文件处理。

### 10.3 质量与评测

- 领域规则用确定性单元测试保护；
- 导入器采用 fixtures 和幂等测试；
- 每增加一个 Agent 工具就补充正向、失败和越权用例；
- 用少量黄金路径做桌面端 E2E，而不是追求所有界面像素级覆盖；
- 对 Candidate Event、关联和分析建立可重复评测集。

### 10.4 文档

- ADR 记录重要且难以逆转的决定；
- 每个阶段更新 README 的当前能力与下一步；
- 数据格式、工具 Schema 和工作区导出格式保持版本化；
- 用户文档解释“原件、派生物、分析”和“不确定性”的差别。

## 11. 优先级与变更方式

阶段内任务分为三档：

- **Core**：完成该阶段纵向演示所必需；
- **Next**：验证后大概率紧随其后；
- **Explore**：需要原型、数据或用户反馈才能决定。

规划时只锁定当前阶段的 Core。后续阶段保持方向清晰但范围开放；如果某个 Next 能显著改善当前闭环，可以前移，而不必等待整个阶段结束。

以下信号可以触发计划调整：

- 用户记录频率低，说明输入流程需要先简化；
- 待补全项堆积，说明提问策略或候选事件召回需要调整；
- Day One 大包导入成为主要障碍，应优先投入性能和恢复能力；
- 用户主要使用人物/时间线而非 Chat，可提前增强浏览视图；
- Evidence 场景出现得更早，可把 Phase 5 的一部分拉入当前阶段；
- 本地模型体验已足够好，可提前提供 Private 模式默认实现。

## 12. 发布节奏建议

不在缺乏真实开发速度时绑定固定日期。每个阶段采用短迭代，并在纵向演示可用后发布内部版本：

```text
选定一个 Core 用户路径
    ↓
完成数据模型和迁移
    ↓
完成最小 UI + Application Service
    ↓
补充恢复、测试和诊断
    ↓
用真实样例走通
    ↓
发布、收集反馈、调整下一切片
```

一个阶段可以包含多次发布；也可以在依赖清晰时并行探索下一阶段，但不让实验功能破坏当前稳定数据。

## 13. 开工清单

建议按以下顺序进入 Phase 0：

1. 初始化 Monorepo、桌面应用和 CI；
2. 建立 Workspace 与 SQLite migration；
3. 定义 Source、Asset、Event、Revision 的 TypeScript 类型；
4. 写对象保险库的 `put / verify / open` 原型；
5. 用一条手动记录和一个附件走通 IPC；
6. 建立第一份去隐私化 Day One fixture；
7. 把黄金路径纳入自动化测试；
8. 根据原型结果更新 ADR 和下一阶段 Core。

完成这份清单后，团队已经具备持续交付产品切片的基础，不需要等所有长期设计一次定稿。
